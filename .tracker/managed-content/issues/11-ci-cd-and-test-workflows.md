# 11: Managed test, ci and cd workflows

Status: resolved

Blocked by: 06, 10

Spec: `.tracker/managed-content/spec.md`. Decisions: `docs/adr/0006-managed-files-and-bake-lock.md`, `docs/adr/0007-child-spaces-extend-parent-templates.md`.

**What to build:** The workflows several Spaces contribute to are managed. `PythonSpace` ships the test workflow; `ZervGitHubActionsTools` ships ci and cd with the zerv versioning and release jobs, and the jobs other Spaces add (test, pre-commit, publish) come from a bakefile value that is the default of an editable block, so an untouched block follows the Spaces and an edited one is kept. This repo moves over and its CI runs them.

## Comments

- 2026-11-26: Hook versus value. Chose bakefile values (`ci_jobs`, `cd_jobs`), as the ticket specifies. A template hook inside the jobs block gives the same "follows the Spaces until edited" behaviour and would let an inserted job carry pins, but the Python Spaces would then have to change ci.yml through `_get_managed_files()`, which works only when `ZervGitHubActionsTools` comes after them in the MRO: with `class B(ZervGitHubActionsTools, PythonLibSpace)` the Python Space's `_get_managed_files()` runs inside Zerv's `super()` call, before ci.yml is in the mapping, so it has nothing to insert into. Values compose through `_get_ci_jobs()` on `BaseSpace` in any base order (tested with both orders), and the jobs Spaces add today are local workflow calls with no pins. A child Space that needs a pinned job in ci or cd can `edit()` the template, or a repo adds it in the trailing block; add a template hook when that need shows.
- 2026-11-26: Shape. ci and cd: triggers and permissions fixed; `# (editable) versioning and release` over block `versioning` (the zerv jobs, their pins inside it); `# (editable) jobs from Spaces` over block `space_jobs`, whose default is `{{ bakefile.ci_jobs }}` (`cd_jobs` in cd); `# (editable) more jobs below` over `jobs`. This repo's `# ====` section banners were dropped. The hooks return a list of jobs (YAML at column 0), joined with a blank line; `ZervGitHubActionsTools._get_managed_values()` gives the two values, and the hooks are empty on `BaseSpace`.
- 2026-11-26: Deviation for review: `PythonSpace` adds the test and pre-commit jobs (it ships those two workflows, so a Python service using zerv gets them too) and `PythonLibSpace` adds the publish jobs through `super()`, instead of `PythonLibSpace` adding all three. The publish jobs pass `python_version` from `.python-version` (`_get_python_version()`) and leave it out when the file is missing.
- 2026-11-26: test.yml blocks: `test_python_versions`, `test_target_python_version`, `test_os` (the OS list), `test_runs_on`, `test_checkout`, `test_mise`, `test_cache`, `test_codecov`, `test_sonarqube`, `jobs`. The default has no integration job (not every Python repo has `tests/integration/`, and `bake test-integration` fails without it); this repo keeps its `test-integration` job verbatim in the trailing `jobs` block.
- 2026-11-26: This repo: `mc sync --dry-run` refused the three headerless files and `mc sync --force` wrote them; the diffs hold only the header, the `(editable)` notes and the dropped banners. The integration job was then put back into test.yml's trailing block. ci.yml and cd.yml read as untouched defaults (no `editable` entries in `bake.lock`), and `test_python_library_gets_test_pre_commit_and_publish_jobs_as_this_repo` compares a Python library Bakebook's output with them.
- 2026-11-26: Checked here: a second `bake mc sync`, `bake lint`, and `bake setup-dev -ff` (skips the brew platform-tools step and tool upgrades) change nothing; `bake mc lock` then `bake mc sync --refresh --dry-run` (the managed-content part of `bake update`) would write nothing. Not run: a full `bake update` (it upgrades tools and dependencies on the host) and CI (needs a push), so that box stays unticked (everything else in it is done). `bake test` passes (2981).
- 2026-11-26: Ticket 08's pin bump finds the new templates' pins (`test_every_pin_in_the_shipped_templates_is_bumped` globs every shipped `.yml`), the zerv reusable-workflow refs (`wislertt/zerv/.github/workflows/<file>@<sha> # <tag>`) included. Not checked against the real `actions-up`: whether it bumps such a ref when it sits in a step `uses:` of the throwaway workflow.
- 2026-11-26: Checked against the real `actions-up` 2.1.0: on a temp copy of `ci.yml` with the zerv refs set back to v0.8.40, `bump_template_pins(..., min_age_days=0)` bumped all three `wislertt/zerv/.github/workflows/<file>@<sha> # <tag>` refs to v0.8.42 (the throwaway workflow lists them as step `uses:`), with an `actions/checkout` pin bumped alongside as a control. No code change needed.
- 2026-11-26: Decision (developer): `BaseSpace` and the Python Spaces must not know about GitHub Actions; a later Space, outside this spec, will own the jobs and the test workflow. Removed `_get_ci_jobs()`/`_get_cd_jobs()` (and `PythonLibSpace._publish_job`, `REGISTRY_TOKENS`) and the `ci_jobs`/`cd_jobs` values. ci and cd keep block `space_jobs` (so no repo edit is dropped), now empty under `# (editable) jobs`, filled by hand. `PythonSpace` no longer writes `test.yml`; the template stays in the package, listed in `TemplateSuite(unused=...)`, which lets a listed template have no Space and fails when a listed one is missing or written by a Space. This repo keeps its test, pre-commit and publish jobs as `space_jobs` edits locked in `bake.lock`, and `.github/workflows/test.yml` is a hand file: unchanged on disk (header included, as for a dropped or detached file) and out of `bake.lock`.
- 2026-11-26: Decision (developer): `PythonSpace` and `PythonLibSpace` know nothing of GitHub Actions. `PythonSpace` no longer writes `pre-commit.yml` and `PythonLibSpace` no longer writes `publish.yml`; both templates stay in `bakelib/space/managed/`, listed in `TemplateSuite(unused=...)` next to `test.yml`, and their expected and blocks files are deleted (the suite renders no case for an unused template). They stay out of `ZervGitHubActionsTools` because they are Python-specific (uv, PyPI); a later combined Space will own them. Ticket 08's pin bump still covers their pins (it globs every shipped `.yml`). This repo declares all three in `MyBakebook._get_managed_files()` with `ManagedFile("bakelib.space", ...)`, the anchor the Spaces used, so the `bake.lock` keys (`bakefile:<name>`) are unchanged. `bake mc sync` left the three files unchanged on disk; `test.yml` is managed again, back in `bake.lock` with its `test-integration` job as the `jobs` edit. Tests now assert that both Python Spaces write nothing under `.github/`, and the workflow tests render the templates through a test Space that declares them as `bakefile.py` does.
- 2026-11-27: Since `6ca6210` the `bake.lock` keys are stored as declared, so this repo's entries read `bakelib.space:<name>` rather than `bakefile:<name>`.
