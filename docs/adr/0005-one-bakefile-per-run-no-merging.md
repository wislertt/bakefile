# One `bakefile.py` per run: nearest, then global, no merging

`bake` and `bakefile` load exactly one `bakefile.py` per run. They walk up from the current directory (or `-C`) and take the nearest one. If none is found, they fall back to the Global `bakefile.py` when the user has created one (`$BAKE_CONFIG_DIR`, else `$XDG_CONFIG_HOME/bake/`, else `~/.config/bake/`). `-g` always picks the global one. `-f` only changes the file name, so walk-up, fallback and `-g` all look for that name. `-C` names an exact directory, so it disables both walk-up and fallback, and a command missing from the chosen Bakebook is an error, not a lookup in the next layer. People will rely on the fallback, so removing it later would break them.

The obvious alternative was mise-style layering, where every config from the current directory up to global is merged and a closer task shadows a farther one. Mise can merge cheaply because its tasks are TOML data. A Bakebook is live Python: every `bakefile.py` is imported under the fixed module name `bakefile`, and layers can need different environments (a Bakefile-level global next to a Project-level repo file), so merging would mean one subprocess per layer and routing each command to the layer that defines it. just and go-task also pick a single file and offer an explicit global flag. Commands run in the chosen `bakefile.py`'s directory, and `ctx.invocation_dir` gives commands that need it the directory `bake` was called from.
