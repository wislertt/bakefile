**bakelib** is an optional collection of opinionated helpers built on top of Bakebook. Install it with the `lib` extra:

```bash
pip install "bakefile[lib]"
```

bakelib is optional. bakefile works without it, and you can write your own Bakebook classes if you prefer different conventions.

A **Space** is a Bakebook preconfigured for a project type. Spaces share a common base and compose through inheritance: `BaseSpace` holds the shared tasks (lint, clean, setup-dev, tools, update, version), then `PythonSpace` and `RustSpace` add language-specific lint, test, and tool setup, and `PythonLibSpace` and `RustLibSpace` add publishing on top. `GitHubActionsTools`, `BaseServiceSpace`, and `SubmodulesUtils` extend `BaseSpace` directly.

How these helpers earn their keep across real repos: [bakefile in practice: the supporting cast](https://wisl.dev/blog/bakefile-supporting-cast/).

## Prebuilt spaces

- `PythonSpace` - Python lint, test, and dev setup (ruff, ty, deptry, pytest): manages the pre-commit workflow ([Managed content](/bakelib/managed-content))
- `RustSpace` - Rust lint, tool setup, and update (cargo sort and fmt; clippy with `bake lint -s`; rustup, cargo)
- `PythonLibSpace` - `PythonSpace` plus `publish` (PyPI / TestPyPI): manages the publish workflow
- `RustLibSpace` - `RustSpace` plus `publish` (crates.io)
- `GitHubActionsTools` - GitHub Actions linting and updates: manages `.github/renovate.json5` and the security workflow. Lint runs jactionlint with shellcheck, and `bake lint -s` adds its online checks. `jactionlint_profile` defaults to `default`, which covers actionlint and zizmor's regular audits; set it to `correctness` (actionlint's checks only) or `pedantic`, or to `None` to use the `profile` of `.github/jactionlint.yaml`. Its `remove-actionlint` Migration removes `actionlint` from the project's mise config
- `ZervGitHubActionsTools` - `GitHubActionsTools` for repos that version with zerv: manages `.releaserc.mjs` and the semantic pull request workflow ([Managed content](/bakelib/managed-content))
- `BaseServiceSpace` - build / deploy / destroy hooks to override
- `SubmodulesUtils` - sync git submodules
- `FnoxSpace` - age key setup for dev, fnox-backed secret cache ([Secrets](/bakelib/secrets))

## PythonSpace

`PythonSpace` provides common tasks for Python projects:

```python
from bakelib import PythonSpace

bakebook = PythonSpace()
```

Available commands:

- `bake lint` - Run oxfmt, toml-sort, ruff format, ruff check, ty, deptry
- `bake test` - Run pytest with coverage on `tests/unit/`
- `bake test-integration` - Run integration tests from `tests/integration/`
- `bake test-all` - Run all tests
- `bake clean` - Clean gitignored files (with exclusions)
- `bake clean-all` - Clean all gitignored files
- `bake setup-dev` - Setup Python development environment
- `bake tools` - List development tools
- `bake update` - Upgrade dependencies (includes uv lock --upgrade)
- ...and more (run `bake --help`)

## Creating custom spaces

Create custom spaces by inheriting from `BaseSpace`:

```python
from bakelib import BaseSpace


class MySpace(BaseSpace):
    def test(self) -> None:
        self.ctx.run("npm test")


bakebook = MySpace()
```

`BaseSpace` provides these tasks (override as needed):

- `lint()` - Run oxfmt. Override the `_lint_fast()` and `_lint_slow()` steps, not `lint()` itself; `bake lint -s` adds the slow steps
- `clean()` / `clean_all()` - Clean gitignored files
- `setup_dev()` - Setup development environment
- `tools()` - List development tools
- `update()` - Upgrade dependencies
- ...and more

Every Space inherits the `remove-prettier-config` Migration from `BaseSpace`: it deletes the prettier config files (`.prettierrc*`, `prettier.config.*`) that oxfmt replaced, now that bakelib manages `oxfmt.config.ts`. It keeps `.prettierignore`, which oxfmt still reads.

A custom Space is a Bakebook like any other - publish it as a package to share it across projects. See [Reuse tasks across projects](/concepts/sharing-tasks).

## Migrations

A **Migration** is a one-off step a Space ships to move projects off something it no longer wants, such as a tool it once added to `mise.toml` or a config file it no longer reads. There is no command for it: `bake lint` fails while a Migration still applies, naming it and how to apply it, `bake setup-dev` applies pending Migrations as its first step, at every `-f` level, and `bake update` applies the upgraded version's Migrations once it has upgraded bakefile.

`bake update --dry-run` previews no Migrations: it upgrades nothing, so it only prints the `bake post-update` step that would apply them. To preview the Migrations that apply now, run `bake --dry-run post-update` or `bake --dry-run setup-dev`.

Write one as a subclass of `Migration` and return it from `_get_migrations()`, extending the parent's dict through `super()`:

```python
from datetime import date

from bake import Context
from bakelib import Migration, PythonSpace


class RemoveOldToolMigration(Migration):
    expires = date(2027, 3, 1)
    description = "Remove old-tool from mise.toml, replaced by new-tool"

    def check(self, ctx: Context) -> bool:
        result = ctx.run(
            "mise list --local --current --json",
            stream=False,
            echo=False,
            capture_output=True,
            dry_run=False,  # check is read-only, so it runs even under --dry-run
            check=False,
        )
        return bool(result and "old-tool" in result.stdout)

    def apply(self, ctx: Context) -> None:
        ctx.run("mise unuse old-tool")


class MySpace(PythonSpace):
    def _get_migrations(self) -> dict[str, Migration]:
        return {**super()._get_migrations(), "remove-old-tool": RemoveOldToolMigration()}
```

The contract:

- `check(ctx)` decides from the project itself whether the Migration still applies. It is read-only and offline, and runs for real under `--dry-run`, so any `ctx.run` it makes passes `dry_run=False`. Nothing records which Migrations ran: once `apply` succeeds, `check` returns false and the Migration does nothing again.
- `apply(ctx)` makes every side effect through `ctx.run`, so `--dry-run` prints the commands without running them. A direct file edit checks `ctx.dry_run` itself and skips the edit when it is set.
- An error raised by `apply` stops the command with exit 2. The next run continues with the Migrations whose `check` is still true.
- Keys are stable kebab-case ids. Migrations run in dict order, parents first, and do not depend on each other.
- `expires` is the date after which the Space author removes the Migration, usually 90 days after the release that adds it.

`bake lint` enforces expiry only in the repo that owns the Migration: one whose class is defined under the project root and not in `site-packages`, such as your Space package installed in editable mode or `bakefile.py` itself. Past its `expires` date, lint fails naming it by key, description and date, so you remove it. A Migration from an installed Space is never checked, so a downstream project does not break because of a date. Lint sees the Migrations of the Spaces your own `bakefile.py` composes; if your package ships Spaces it does not use itself, check their `collect_migrations()` dates in a unit test.

A project that does not want a Migration removes it by key in its own Bakebook:

```python
class MyBakebook(MySpace):
    def _get_migrations(self) -> dict[str, Migration]:
        migrations = super()._get_migrations()
        del migrations["remove-old-tool"]
        return migrations
```

Once upstream removes that Migration, the `del` fails: `bake lint` and `bake setup-dev` exit 2 with a message naming the key, so you delete the dead line.
